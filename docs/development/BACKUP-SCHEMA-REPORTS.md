# Backup schema and report reference

Status: describes the engine sources in the current development checkout, not a release guarantee. The normative field contract is `docs/development/IMPLEMENTATION-CONTRACT.md`; implementation details below are from `src/backup/Manifest.ps1`, `Backup.ps1`, `Recovery.ps1` and `Entry.ps1`.

## Generation layout and lifecycle

The engine creates a unique generation under `PITR-Backups/<computer>/<UTC timestamp>_<short id>/`. A generation has `manifest.json`, `backup-log.txt`, `backup-status.json`, payload directories (`profiles/<source-id>/` and `extra-folders/<source-id>/`), and optionally `recovery/`. The manifest is authoritative; status/log are operational aids. Copy and verification are separate phases. Resume is limited to Running/Interrupted states; a Verified generation is immutable to resume. Verification can be rerun to detect changed stored payload.

Manifest top-level schema v1 (PascalCase): `SchemaVersion`, `BackupId`, `ComputerIdentity`, `OsVersion`, `ApplicationVersion`, `CreatedUtc`, `StartedUtc`, nullable `CompletedUtc`, `State`, `Scope`, `SourceView`, `Consistency`, `Sources`, `Entries`, `Exclusions`, `Warnings`, `Counts`, `RecoveryPackage`, `DestinationIdentity`. `SourceView` is `Live`; `Consistency` is `LiveNotApplicationConsistent`. Lifecycle states include Planned, Running, Interrupted, CopyCompleted, Verifying, Verified, CompletedWithWarnings and Failed. Copy completion is not verification. Full `Verified` requires all selected objects accounted for, no skipped/failed objects, and all copied objects FullVerified; quick verification intentionally cannot create that strongest state.

A source records `Id`, original `Path`, nullable `ProfileSid`, `SourceVolumeId`, `Category` and `DisplayName`. An entry records unique `Id`, `BackupId`, `SourceId`, `OriginalPath`, nullable `ProfileSid`, `RelativePath`, `BackupRelativePath`, `Type`, `Length`, `LastWriteUtc`, `Attributes`, `SourceVolumeId`, `CopyStatus`, `VerificationStatus`, nullable `Sha256`, nullable `Error`, `SourceView`, `IsAdvanced` and `IsSensitive`. Entry types include File, Directory, ReparsePoint, Unsupported and observed special cases such as CloudPlaceholder and Encrypted. Copy outcomes are Pending, Copied, Skipped or Failed; verification outcomes are Pending, QuickVerified, FullVerified or Failed. An exclusion or warning is not evidence that content was backed up.

Counts are generated from recorded entries, including expected/copied/verified/skipped/failed and bytes. Unsupported or unreadable objects are recorded with a reason where discoverable. Inventory failures can make accounting incomplete; consumers must not infer success from a directory's presence or a copy-completed state.

## Recovery comparison and restore reports

`Compare-PitrBackup` returns SchemaVersion, BackupId, ManifestPath, BackupRoot, ManifestState, Deep, MappedSources, Entries, Summary, Warnings, ScanComplete and Complete. Each comparison entry includes IDs/relative paths, backup/current paths, Classification, lengths/timestamps, hashes, `ContentVerified`, advanced/sensitive flags and Error. Classifications: Missing, Different, Identical, LikelyIdentical, CurrentOnly and Unknown. Deep mode hashes current and backup content and checks backup hash against its recorded value. Non-deep metadata agreement is only LikelyIdentical. Current-only scanning is capped at 200,000 files per root; the cap or enumeration/reparse/mapping issues make the scan incomplete and are reported. Unknown is not equality or safety.

`Restore-PitrFiles` returns SchemaVersion, BackupId, ManifestPath, DryRun, ConflictPolicy, AlternateRoot, Actions, Summary, Complete and Warnings. Each action states the selected entry, operation, destination, preserved path, result, verification status and error. It recomputes a deep comparison, validates backup hash, requires explicit entry IDs and an approved mapping or alternate root, and defaults to dry-run. Existing files default to Skip. Alongside preserves the existing file; Replace preserves it to a unique conflict path before swapping. Advanced AppData requires explicit consent; sensitive targets are blocked from live-profile restoration. `CurrentOnly` entries are never targets. A report with skipped actions is not proof that all requested recovery occurred.

`Export-PitrReport` supports Json, Csv and Text. CSV emits comparison entries or restore actions with formula-prefix mitigation and quoting. Text/CSV/JSON can expose private filenames and paths; reports are local output, not anonymized. CLI JSON is printed when requested; CSV stdout is intentionally refused unless `--output` is given. CLI exit codes documented in help: 0 complete, 2 warnings/incomplete, 3 invalid input/operation failure, 4 verification failure, 5 missing explicit recovery authorization/selection. Review structured `Complete`/`ScanComplete`, per-item results and warnings, not only exit code.

## Implementation gaps and acceptance matrix

| Area | Current evidence | Gap / consequence |
|---|---|---|
| Live copy and accounting | `Backup.ps1` streams ordinary file bytes, hashes, logs and records explicit outcomes; it does not create VSS snapshots. | Not application-consistent. App writers must be closed; live-changing sources may not represent a single instant. |
| Destination safety | `Platform.ps1` resolves volume identity and validates destination/source relationships and writeability. | Real Windows volume/network/reparse behavior still needs current-tree Windows testing. |
| Profile discovery/scopes | ProfileList registrations plus Public; Complete inventories profile roots; Personal enumerates conventional existing folders; Custom is explicit. | Redirected folders are not automatically enumerated; Personal warns to review redirection/cloud and use Custom. Full redirected-folder and unusual ProfileList cases need Windows evidence. |
| Manifest validation | `Manifest.ps1` owns schema/path validation, hashing and transactional writes. | Does not make a changed or hostile backup trustworthy; inspect code/inventory provenance and retain external trusted source. |
| Recovery launcher | `Backup.ps1` packages trusted modules, launcher, README and SHA-256 inventory; launcher resolves manifest relatively. | Inventory is not signed; Windows package extraction and independent launch remain pending. |
| Compare/recover engine | `Recovery.ps1` implements explicit mapping, six classifications, deep hash compare, explicit selection, dry-run, conflict preservation and path checks. | Reparse/ACL/cloud/EFS/long-path behavior and hostile filesystem races need Windows review/testing. No causal attribution to PITR. |
| Reports and CLI | `Cli.ps1` parser/help defines backup create/verify/resume/list and recover compare/restore; `Entry.ps1` routes formats and status exits. | Documentation command examples are source-checked, but live help execution was blocked in this environment (see continuation evidence). |
| GUI | `Ui.ps1` has a recovery window with evolving controls. | Concurrent UI lane still owns conflict/filter/report controls; do not assume the complete wizard, all ten-language coverage, readiness, keyboard/DPI/small-screen or interaction acceptance. |
| Platform/release validation | Current work is on a Linux development host. | No claim of Windows PowerShell 5.1, Windows 11, current-tree CI, actual PITR, NAS interruption, live-app, cloud/EFS, scale or performance verification. No measurements are asserted here. |

No report can prove restore-point availability or that rollback happened. This subsystem is user-file backup and selective file recovery only; image/system restore, automatic PITR, reboot, WinRE changes and credential persistence are out of scope.
