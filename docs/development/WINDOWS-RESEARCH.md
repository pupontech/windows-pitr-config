# Windows implementation research

Status: authoritative documentation researched; native API implementation/runtime proof is separate. No live Windows/PITR or VSS experiment is claimed.

## PITR and temporary VSS
[Microsoft PITR documentation](https://learn.microsoft.com/en-us/windows/configuration/point-in-time-restore) says restore points include local user files, run restoration from WinRE, may require BitLocker recovery keys, and share VSS storage with other tools. Storage pressure can evict existing points. The upstream project additionally documents OS-volume-only behavior based on PITR binary inspection. New backup must reject the resolved actual OS volume independently of drive letter.

[Microsoft VSS backup lifecycle](https://learn.microsoft.com/en-us/windows/win32/vss/overview-of-processing-a-backup-under-vss) requires requester/writer coordination, writer metadata, component selection and notifications before/after snapshot and backup. A basic Win32_ShadowCopy create call is not proof of application-consistent backup. Implementing a validated writer-aware requester without extra binaries is a substantial separate component and can consume shared PITR storage. Initial safe fallback: ordinary live copy, no VSS/PITR mutations, identify copy/mutation errors and explicitly label LiveNotApplicationConsistent. Browser/email/database/hive readability is not internal consistency. Close applications first; active database integrity requires application-specific validation. No unsupported persistent snapshot creation or deletion is permitted.

## Resolve identity, not spelling
[GetFinalPathNameByHandleW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew) returns the fully resolved target path, including symlink targets. VOLUME_NAME_GUID provides a stable volume GUID for local volumes; UNC shares have no such GUID and may return ERROR_PATH_NOT_FOUND for that mode. SMB normalized-path queries may fail if intermediate components are inaccessible. Grow buffers using returned required length, treat errors explicitly, dispose handles. Use existing nearest ancestor for a proposed nonexistent destination, but validate again after creation/before writing. An ancestor string check alone cannot defeat adversarial concurrent reparse replacement; fail-closed no-follow handle/identity checks remain a security-review requirement.

[GetVolumePathNameW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumepathnamew) finds the final volume mount point, including nested mounted folders/junctions. Relative/invalid unqualified paths can misleadingly resolve to boot volume; require an absolute validated path first. NT device paths are not accepted as normal Win32 input. SMB does not support volume management functions, so never turn a failed local-volume query into an assumption that a network path is safe.

[WNetGetUniversalNameW](https://learn.microsoft.com/en-us/windows/win32/api/winnetwk/nf-winnetwk-wnetgetuniversalnamew) resolves mapped network drives to UNC. Persist the UNC reference rather than the temporary drive letter; no credentials. Explicitly detect/reject loopback, machine-name, IP/FQDN aliases to this host, not just literal localhost. Remote storage independence/failure domains cannot generally be proven by a client; show that limitation. Same physical local disk on a different volume avoids PITR rollback but not disk failure. External separate media is preferred.

## File special cases
[Microsoft file attributes](https://learn.microsoft.com/en-us/windows/win32/fileio/file-attribute-constants) distinguishes ReparsePoint, SparseFile, Offline, Encrypted and recall attributes. Hidden/System are inclusion attributes, not automatic exclusions. Do not open online-only content for hashing/copy merely to see whether it hydrates: detect unavailable cloud/reparse state first and report unavailable/unsupported. Never recurse directory reparse points. Do not assume every reparse point is a cloud file or every cloud folder name proves a provider.

EFS means encrypted streams, not portable credentials. Ordinary readable plaintext copy is not proof that original encrypted recovery prerequisites survive PITR; record encryption explicitly, don't export keys or promise decryptability. Alternate data streams and hardlink identity need separate enumeration; copying only unnamed data streams must be disclosed per file and forbid claiming metadata-complete backup. Sparse/compressed logical bytes may expand at destination; logical size is a conservative capacity basis plus overhead. Permissions/owner/audit cannot safely be copied wholesale across accounts/filesystems; don't reset ownership or bypass ACL restrictions. Protect destination confidentiality through the destination's access controls and established drive encryption, not custom crypto.

## Copy adapter decision and benchmark gate
[Robocopy documentation](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/robocopy) documents /Z restartable copy, /COPY:DAT attributes/timestamps, /XJ exclusions, retry options and exit-code distinctions. /B and /ZB bypass permission restrictions and are not appropriate here. /MIR,/PURGE,/MOVE,/MOV are prohibited. Default huge retry counts must never be inherited. Codes 0-7 still require per-file inventory verification; >=8 failures. Robocopy process success is not backup completeness.

A native streaming .NET adapter simplifies per-file source/destination hashing, cancellation, manifest accounting and verified temp-file promotion, while bounded buffers avoid reading whole files. This is an engineering rationale, not a measured performance verdict. Benchmark .NET and non-destructive Robocopy on identical test-owned file trees, new destinations per adapter, exact logical file/byte counts, bounded retries, measured wall/CPU/memory where available and full destination hashes. Label cache effects, dataset scale, filesystem and OS. Do not infer hundred-GB performance from small CI fixtures. Report real numbers only after execution.
